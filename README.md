# dotfiles

Everything needed to turn a fresh Arch Linux install into this machine:
the configs, the package list, the three programs built from source
(dwl, slstatus, swhkd), the SDDM theme, and the system files under `/etc`.

Two tools, nothing else: **git** stores it, **GNU Stow** links it into place.

```
git clone <this repo> ~/.dotfiles
~/.dotfiles/install.sh
```

That is the whole restore. The rest of this file explains what is in here,
how it works, and how to keep it current.

---

## 1. Layout

```
~/.dotfiles/
├── install.sh          bootstrap a fresh machine (idempotent, step by step)
├── sync.sh             refresh the snapshots below from the live machine
├── README.md           this file
├── .gitignore          keeps *.bak, *.orig, *.rej, *.log and .claude/ out
│
├── home/               ── GNU Stow packages, one directory per program ──
│   ├── bash/.bashrc, .bash_profile, .bash_logout
│   ├── bin/.local/bin/*            your scripts (startwl.sh, usb-mount, wifi-menu, ...)
│   ├── foot/.config/foot/foot.ini
│   ├── swhkd/.config/swhkd/swhkdrc keybindings
│   ├── mako/  zathura/  fastfetch/  htop/  newsboat/  swayimg/  glow/
│   ├── vim/.vim/…      git/.gitconfig      irssi/.irssi/…
│   ├── systemd/.config/systemd/user/battery-warn.{service,timer}
│   ├── xdg/.config/mimeapps.list, xdg-desktop-portal/portals.conf
│   └── wallpaper/Pictures/dedsecx4.jpg
│
├── packages/           ── generated by sync.sh ──
│   ├── native.txt      explicitly installed repo packages   (pacman -Qqen)
│   └── aur.txt         explicitly installed AUR packages    (pacman -Qqem)
│
├── system/
│   ├── rootfs/         files copied to the same path under / as root
│   │   ├── etc/doas.conf
│   │   ├── etc/sddm.conf.d/10-wrench.conf
│   │   ├── usr/local/bin/dwl-session
│   │   └── usr/share/sddm/themes/wrench/   your SDDM theme
│   ├── services-system.txt   enabled system units   (generated)
│   ├── services-user.txt     enabled user units     (generated)
│   └── groups.txt            your group membership  (generated)
│
└── src/                ── programs built from source ──
    ├── sources.conf    repo URL + pinned commit for each one
    ├── dwl/dwl.patch   your changes to dwl (bar, gaps, XWayland, keybinds)
    ├── dwl/drwl.h      new file the bar patch needs
    └── slstatus/slstatus.patch
```

Three kinds of content live here, and they are maintained differently:

| Kind | Where | How it stays current |
|---|---|---|
| Config files | `home/` | Automatically. They are symlinked, so editing the live file edits the repo. |
| Snapshots of system state | `packages/`, `system/*.txt`, `system/rootfs/`, `src/` | Run `./sync.sh` before you commit. |
| Scripts and this README | top level | By hand. |

## 2. How GNU Stow is used

Stow manages symlinks. Each directory under `home/` is a **package** whose
contents mirror your home directory:

```
home/foot/.config/foot/foot.ini       ←  package "foot"
```

`stow -d ~/.dotfiles/home -t ~ foot` creates

```
~/.config/foot/foot.ini  →  ../../.dotfiles/home/foot/.config/foot/foot.ini
```

The live file **is** the repo file. There is no copy step and nothing to
forget: `git status` in `~/.dotfiles` always shows exactly what changed on
the machine. This is the reason stow was chosen over a bare git repo or a
copy script — both of those let the repo drift silently, which is how the
previous dotfiles repo ended up describing an X11 setup on a Wayland machine.

Things worth knowing:

- **Links are relative** (`../../.dotfiles/...`). Moving `~/.dotfiles`
  somewhere else breaks every link. Keep it where it is; if you ever must
  move it, run `stow -D` first (see §4), move, then stow again.
- **Folding.** If a directory does not exist in `~` yet, stow links the whole
  directory instead of each file. `~/.config/foot` existed here, so its
  files are linked one by one and `foot.ini.bak` next to them is untouched.
  On a fresh install `~/.config/foot` will not exist, so stow creates
  `~/.config/foot → ../.dotfiles/home/foot/.config/foot` — a directory link.
  Both work identically. One consequence: if a program then writes a *new*
  file into a folded directory, that file lands inside the repo and shows up
  in `git status`. Either add it or delete it.
- **Conflicts.** Stow never overwrites a real file. If one is in the way it
  prints `existing target is neither a link nor a directory: .bashrc` and
  does nothing. `install.sh` moves such files to
  `~/.dotfiles-backup-<date>/` before stowing; by hand, do the same or use
  `--adopt` (§4).
- **Packages are independent.** On another machine you can stow a subset:
  `stow -d ~/.dotfiles/home -t ~ bash vim git` and leave the desktop
  packages out.
- **`.git`, `README*`, `LICENSE`** and similar are ignored by stow's built-in
  ignore list, so top-level files never get linked into `~`.

## 3. Fresh install, step by step

### Before running anything

1. Install Arch normally (archinstall or manual). Create your user, give it
   sudo through `wheel` or know the root password — the script needs root
   for the first steps and only switches to doas once it has installed it.
2. Same username as here matters for `doas.conf`, which names the user
   (`permit nopass omdaughh as root`). Different username → edit
   `system/rootfs/etc/doas.conf`.
3. Network up, then `pacman -S git` and clone:

```
git clone <this repo> ~/.dotfiles
cd ~/.dotfiles
./install.sh
```

Total time is dominated by package downloads and building yay and swhkd
(Rust); expect 20–40 minutes.

### What `install.sh` does, in order

| Step | What | Why this position |
|---|---|---|
| `packages` | `pacman -Syu --needed` everything in `packages/native.txt` | Everything later depends on it (stow, doas, build tools, wlroots). |
| `doas` | Copies `doas.conf` to `/etc` | So every later root command uses doas, as on this machine. |
| `yay` | Clones `aur/yay` into `~/Desktop/src/yay` and builds it | yay is itself an AUR package; nothing else can install it. |
| `aur` | `yay -S --needed` everything in `packages/aur.txt` | wlroots0.19 comes from here and dwl needs it to build. |
| `stow` | Backs up conflicting skel files, then `stow -R` all `home/*` | Configs and `~/.local/bin` scripts in place before the session tries to use them. |
| `system` | Copies `system/rootfs/**` to `/` with the same modes | doas.conf, SDDM config and theme, `dwl-session`. |
| `sources` | Clones, patches, builds and installs dwl, slstatus, swhkd | Needs base-devel, wlroots, rustup from earlier steps. |
| `services` | `systemctl enable` system and user units | sddm, NetworkManager, libvirtd, pipewire, battery-warn.timer. |
| `groups` | `usermod -aG` wheel, libvirt | Takes effect at next login. |

Every step checks before acting: packages already present are skipped by
`--needed`, binaries already installed skip the build, units already enabled
are no-ops. Running the script twice is safe. Run a single step by name:

```
./install.sh stow
./install.sh sources
```

Preview without changing anything:

```
DRY_RUN=1 ./install.sh
```

If one package in a list has been renamed or dropped from the repos, the
batch install fails and the script falls back to installing one at a time,
then prints the ones it could not install. It never aborts on that.

### After it finishes

Reboot. SDDM comes up with the wrench theme; choose the **dwl** session.
`dwl-session` execs `~/.local/bin/startwl.sh`, which starts slstatus → dwl,
then swaybg, mako, swhks + swhkd, usb-mount and lock-daemon — exactly what
runs here.

### What it deliberately does not restore

- `~/.ssh`, `~/.gnupg`, API tokens, `~/.config/kaggle` — secrets never go in
  this repo. Keep them in an encrypted backup (`gpg-backup` in your bin
  helps) and restore by hand.
- `~/.local/share/fonts/Thmanyah` — 2.6 MB of personal fonts. Copy them
  back by hand, or add a `fonts/` stow package if you decide they belong.
- Pentest tools in `/usr/local/bin` (nuclei, gospider, gf, shef, jam, uro)
  — installed with `go install` or by hand, not tracked.
- Browser profiles, Obsidian vault, Discord/Spotify state, `~/envs`
  virtualenvs, `~/.newsboat` (legacy dir; the live config is
  `~/.config/newsboat`).
- Hostname, locale, keymap, bootloader, disk layout — those are the Arch
  install itself, done before this script runs.

## 4. Day-to-day: managing configs

### Editing a config

Nothing special. Edit `~/.config/foot/foot.ini` as always. It is a symlink,
so the change is already in the repo:

```
cd ~/.dotfiles && git status     # shows home/foot/.config/foot/foot.ini modified
git add -A && git commit
```

### Adding a file to an existing package

Say mako grows a second file `~/.config/mako/extra`. Move it into the
package and restow:

```
mv ~/.config/mako/extra ~/.dotfiles/home/mako/.config/mako/
stow -R -d ~/.dotfiles/home -t ~ mako
```

`-R` (restow) unlinks and relinks the package so the new file gets its
symlink. `./sync.sh` runs `stow -R` on every package, so it does this for
you as well.

### Adding a new program

```
mkdir -p ~/.dotfiles/home/waybar/.config/waybar
mv ~/.config/waybar/config ~/.dotfiles/home/waybar/.config/waybar/
stow -d ~/.dotfiles/home -t ~ waybar
```

The package name (`waybar`) is yours to choose; the path *inside* the
package must mirror `~` exactly.

Shortcut when the files already exist in `~` and you want stow to pull
them in for you: create the package with **copies** of the files, then

```
stow --adopt -d ~/.dotfiles/home -t ~ waybar
```

`--adopt` moves the live files into the package (overwriting the copies)
and replaces them with symlinks. That is how this repo was populated.
Careful: adopt overwrites what is in the package with what is in `~`, so
only use it when the package copy is not the newer version.

### Removing a config from the repo

```
stow -D -d ~/.dotfiles/home -t ~ glow      # remove the symlinks
git rm -r ~/.dotfiles/home/glow            # remove from the repo
```

If you still want the file on disk afterwards, copy it out of the package
before `git rm`.

### Checking what is linked

```
find ~ -maxdepth 3 -type l -lname '*/.dotfiles/*'
```

Broken links (a file was removed from the repo but the link stayed) show up
with `find ~ -xtype l`. Fix with `stow -R` on that package.

## 5. Keeping the snapshots current: `sync.sh`

Configs sync themselves. Everything else is a snapshot that goes stale as
you use the machine: you install a package, enable a service, edit
`/etc/doas.conf`, change a keybind in dwl's `config.def.h`. `sync.sh`
regenerates all of that from the live machine:

```
./sync.sh
```

It rewrites, in this order:

1. `packages/native.txt` and `packages/aur.txt` from pacman, minus the
   `EXCLUDE` pattern at the top of the script (currently `chezmoi`,
   `lib32-glibc`, `yay`, `*-debug` — each with a comment saying why).
2. `system/services-*.txt` and `system/groups.txt` from systemctl and `id`.
3. `system/rootfs/**` — copies the live version of every file already
   tracked there. It does not discover new files; to start tracking one,
   create it at the mirrored path once (`system/rootfs/etc/foo.conf`),
   and every later sync refreshes it.
4. `src/sources.conf` commits and `src/*/*.patch` from the clones under
   `~/Desktop/src` (see §6).
5. `stow -R` on every package, then `git status`.

It never commits. Read the diff, then:

```
git add -A && git commit
```

Do this before any `git push`, and any time you have changed the system in
a way you would want back. A reasonable habit: after every
`pacman -S`/`yay -S` that you intend to keep.

To stop tracking a package you uninstalled: uninstall it, run sync, it is
gone from the list. To keep a package installed but out of the restore
list: add it to `EXCLUDE`.

## 6. Programs built from source

dwl, slstatus and swhkd are not packages. Your customised versions are
reproduced from three things per program, all in `src/`:

- an **upstream repo URL** and a **pinned commit** in `sources.conf`
- a **patch** = `git diff HEAD` of your working tree against that commit
- any **new files** the patch needs (`drwl.h` for dwl's bar)

`install.sh sources` clones the upstream at the pinned commit, drops in the
new files, applies the patch, runs `make`, and installs as root. For swhkd
it installs the two binaries by hand (with the setuid bit the daemon needs)
because upstream's `make install` hard-codes `sudo`.

The clones live in `~/Desktop/src/<name>` — the same place they are now —
so on this machine the script sees your existing, uncommitted working trees
and builds them **as they are** without touching them. On a fresh machine
it recreates them from the patch.

### Changing a keybind or anything else in dwl

```
cd ~/Desktop/src/dwl
vim config.def.h          # edit
make && doas make install # rebuild, reinstall
cd ~/.dotfiles && ./sync.sh && git add -A && git commit
```

`sync.sh` refreshes `src/dwl/dwl.patch` from your working tree. The same
applies to slstatus (`config.def.h`). swhkd has no local changes; its config
is `~/.config/swhkd/swhkdrc`, a stow-managed file.

### Upgrading to a newer upstream

```
cd ~/Desktop/src/dwl
git stash                 # park your changes
git pull                  # move to newer upstream
git stash pop             # reapply; resolve conflicts if any
make && doas make install
cd ~/.dotfiles && ./sync.sh   # re-pins the commit and regenerates the patch
```

The patch is only guaranteed to apply at the pinned commit. If you pull
upstream *without* rebuilding and syncing, the pin and the patch still
describe the old, working state — which is what you want in a backup.

### About the GitHub fork

`github.com/3omdaughh/dwl` is a fork of the old GitHub mirror; its last
commit is from November 2023 (v0.5, "add notice about Codeberg migration").
Upstream moved to Codeberg and your local clone is a v0.7-era commit from
there. The fork does not contain that commit, so `sources.conf` points at
Codeberg. If you want the fork to be the source of truth:

```
cd ~/Desktop/src/dwl
git remote add fork git@github.com:3omdaughh/dwl.git
git checkout -b mine && git add -A && git commit -m "my dwl"
git push fork main mine      # main = upstream history the fork lacks
```

then set `DWL_REPO` in `src/sources.conf` to the fork URL. Nothing else
changes; the patch is still applied on top of the pinned commit.

## 7. System files (`system/rootfs`)

`system/rootfs/` mirrors `/`. `install.sh system` copies every file in it
to the same path under `/`, as root, preserving the mode bits git tracks.
`sync.sh` copies the live versions back. Tracked today:

- `/etc/doas.conf` — `permit nopass omdaughh as root`
- `/etc/sddm.conf.d/10-wrench.conf` — Wayland greeter via weston, wrench theme
- `/usr/local/bin/dwl-session` — what SDDM's dwl session execs
- `/usr/share/sddm/themes/wrench/` — your theme (1.2 MB, mostly background.png)

To track another file, create it at the mirrored path once:

```
install -Dm644 /etc/pacman.conf ~/.dotfiles/system/rootfs/etc/pacman.conf
```

From then on `sync.sh` keeps it fresh and `install.sh` restores it.

Nothing else under `/etc` differs from package defaults on this machine
(checked with pacman's backup-file checksums), so nothing else is tracked.
`mkinitcpio.conf`, `locale.gen`, `vconsole.conf`, `fstab` and `grub` are
all what archinstall produced.

## 8. Testing the restore

An untested restore is a guess. Before you need it:

```
doas pacman -S arch-install-scripts        # once
mkdir ~/arch-test
doas pacstrap -K ~/arch-test base base-devel git sudo
doas systemd-nspawn -D ~/arch-test --bind-ro=$HOME/.dotfiles:/root/dotfiles
```

Inside: create your user, give it a sudoers rule, clone or copy the repo,
run `install.sh`. Steps that need a display (`sddm`) or hardware will fail
in a container — that is fine; you are checking that packages resolve, the
patches apply, the source builds compile, and stow lays out `~` correctly.
A qemu VM with the Arch ISO tests the rest.

## 9. Troubleshooting

**`existing target is neither a link nor a directory`** — a real file is
where stow wants a symlink. Move it away (or delete it) and re-run. On a
fresh install `install.sh` does this for you.

**`existing target is not owned by stow`** — a symlink is in the way that
points somewhere other than this repo. Remove it and re-run.

**Config edits do not show in `git status`** — the file is a real file,
not a symlink. Something replaced the link (some programs save by
write-new-file-then-rename, which breaks symlinks). Move the file into the
package and `stow -R`.

**`patch does not apply`** during `install.sh sources` — the pinned commit
in `sources.conf` and the patch disagree, usually because someone pulled
upstream and synced only one of them. Check out the pinned commit in the
clone and regenerate with `sync.sh`, or update the pin.

**`systemctl --user` fails during install** — no user session bus yet
(happens over ssh). Log in on the machine, then `./install.sh services`.

**Links broke after moving `~/.dotfiles`** — see §2; links are relative.
Move it back, or `stow -D` everything from the old path and stow again
from the new one.

**A package in `native.txt` no longer exists** — install continues without
it and lists it at the end. Remove it from the machine or add it to
`EXCLUDE`, then `sync.sh`.

## 10. Cheat sheet

```
# restore a fresh machine
git clone <repo> ~/.dotfiles && ~/.dotfiles/install.sh

# after changing packages / services / /etc / dwl source
cd ~/.dotfiles && ./sync.sh && git add -A && git commit

# link / relink / unlink one package
stow    -d ~/.dotfiles/home -t ~ foot
stow -R -d ~/.dotfiles/home -t ~ foot
stow -D -d ~/.dotfiles/home -t ~ foot

# pull existing live files into a new package
mkdir -p ~/.dotfiles/home/NAME/.config/NAME && cp ~/.config/NAME/* $_
stow --adopt -d ~/.dotfiles/home -t ~ NAME

# dry-run either script's effect
stow -n -v -d ~/.dotfiles/home -t ~ foot
DRY_RUN=1 ~/.dotfiles/install.sh

# rebuild dwl / slstatus / swhkd from the repo's patches
FORCE_BUILD=1 ~/.dotfiles/install.sh sources
```
